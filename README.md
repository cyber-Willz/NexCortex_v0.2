# nexgraph 0.22 vs other graph databases — benchmark report

*Measured 26 Nov 2026 in a sandbox (1 vCPU, 3 GB RAM, Ubuntu 24.04, rustc 1.91). Archive: `nex_workspace_perf_tar.gz` → `nexgraph/nexgraph` (v0.22.0).*

## Bottom line

- **Among the graph databases tested, nexgraph is fastest on small, indexed, selective queries** (point lookup, 1-hop, 2-hop; only in-process SQLite is faster). It is roughly 40–130× faster than Kuzu, Ladybug and DuckDB on these, but that gap is mostly *call overhead*: nexgraph runs in-process from Rust, the others are driven from Python (see "How to read this").
- **It is not the fastest graph engine on traversals.** FalkorDB, even though it is driven over a socket from Python, beats nexgraph on distinct multi-hop reachability (**409.0 µs vs 1.1 ms**) and on shortest path (**284.8 µs vs 2.0 ms**, ~7×). Plain SQLite with an index on the edge table is also ~2× faster than nexgraph on reach3, and faster on point, 1-hop and 2-hop lookups.
- **On analytics nexgraph is competitive with the columnar graph engines, but not with DuckDB.** It matches Kuzu on group-by and is ~2.6× faster than Kuzu on the `WITH` aggregate, but DuckDB is ~2.4× faster on group-by and ~2.3× faster on `WITH`. FalkorDB is ~7× slower than nexgraph on both.
- **Bulk load is slower than the columnar engines** (≈1.3 s vs ≈0.9–1.0 s for Kuzu/Ladybug/DuckDB) and ~57× faster than FalkorDB's Cypher `UNWIND` load.
- **Correctness:** every system returned identical results for every workload it ran (checksums over all queries matched nexgraph's).
- **Not measured:** Neo4j and Memgraph (no Docker daemon, vendor download hosts are not reachable from the sandbox), so the comparison does **not** include the two most widely deployed graph databases.

## Setup

**Graph:** 100,000 nodes, 1,000,000 directed edges, skewed targets (a few hubs), seed 7, generated by `bench/gen_data.py` (the harness shipped in the archive). Max out-degree 26. Same data, same query semantics and the same checksum rules for every system.

**Systems**

| System | Type | How it was driven |
|---|---|---|
| nexgraph 0.22 | Embedded property-hypergraph DB (Rust, row-at-a-time, MVCC) | In-process Rust (`examples/bench_compare`), in-memory database, `--release` (LTO) |
| Kuzu 0.11.3 | Embedded columnar graph DB (C++) | Python binding, prepared statements |
| Ladybug 0.15.3 (`real_ladybug`) | Kuzu fork, same engine lineage | Python binding, prepared statements |
| FalkorDB (falkordblite 0.12.2) | Sparse-matrix (GraphBLAS) graph DB on Redis | Embedded server process, Python client over a local socket |
| DuckDB 2.0.1 | Columnar analytical SQL engine, **not a graph DB** | Python, edge table + index on `e(a)` |
| SQLite 3.45.1 | Row-store SQL engine, **not a graph DB** | Python `sqlite3`, edge table + index on `e(a)` |

DuckDB and SQLite are included as relational baselines: they show what a plain edge table with an index achieves without a graph engine. Shortest path was not run on them (a recursive-CTE BFS is not a like-for-like workload).

**Method:** nexgraph, Kuzu, Ladybug, DuckDB and SQLite were each run 3 times and the table shows the median of the per-run medians. FalkorDB was run once (its load alone takes ~77 s). Point/hop workloads: 2,000 / 2,000 / 500 / 100 queries with warm-up; shortest path: 55 pairs after 5 warm-up; scan, group-by and `WITH` workloads: median of 3 executions per run. Systems ran one at a time on the single vCPU.

## How to read this

1. **Call overhead dominates the small queries.** nexgraph's per-call floor is ~0.5 µs because it is a Rust function call; Kuzu/Ladybug cost ~32–34 µs and DuckDB ~103 µs for a trivial query through the Python binding, and FalkorDB ~41 µs over a socket. The 100×-plus gaps on point/hop queries are mostly this, not engine speed. SQLite is also in-process and shows what a bare row store does with the same call overhead: it is *faster* than nexgraph on point lookups (1.7 vs 3.2 µs) and 1-hop (2.9 vs 6.9 µs) and 2-hop (15.6 vs 28.6 µs). Among graph engines, FalkorDB is the better "like for like on a client/server basis" reference: it pays a socket round trip per query and still beats nexgraph on the traversal-heavy rows.
2. **Where nexgraph's engine is genuinely behind:** distinct multi-hop reachability and shortest path (FalkorDB 2.8× and ~7× faster), group-by/`WITH` analytics against DuckDB, and bulk load against the columnar engines. This agrees with the project's own `docs/performance.md`, which attributes the analytics gap to row-at-a-time execution and scattered property reads and lists columnar storage and batched execution as unbuilt.
3. **Where it holds up:** against the other *graph* engines on aggregates (parity with Kuzu/Ladybug on group-by, ~2.6× faster on `WITH`) and on indexed point/hop queries once call overhead is allowed for (hop2 net of floor: nexgraph ~28 µs vs Kuzu ~2.7 ms and FalkorDB ~126 µs net).
4. **The full-scan row is not a reliable comparison.** Ladybug, DuckDB and SQLite answer `count(*)` over the edge set from table metadata or a single tight loop (92–670 µs), so they are not really scanning 1M edges; Kuzu (7.0 ms) and nexgraph (4.0 ms, via its factorised count fast path) do more work. nexgraph's own README reports 28 ms for this on a 2-vCPU VM; here it was 3.3–4.4 ms across runs. Treat this row as indicative only.
5. **Shared, small VM.** One vCPU, 3 GB, run-to-run variation is visible in the spread table. Results at 100k nodes / 1M edges say nothing about 100M+ edges, concurrency (nexgraph has a single writer; nothing here tests concurrent clients), or durability costs (nexgraph, DuckDB and SQLite ran in-memory; Kuzu, Ladybug and FalkorDB used their default on-disk configuration).
6. **Query text is not identical.** Each system uses its own dialect (Kuzu `* SHORTEST`, FalkorDB `shortestPath()` in `RETURN`, nexgraph `CALL algo.shortestPath`, SQL joins for the relational baselines). Result checksums are identical, which is the correctness check.




Rust toolchain: the sandbox had none, so rustc/cargo 1.91 were installed from Ubuntu's `rustc-1.91` package (the crate requires ≥ 1.85). The Ladybug, FalkorDB and SQL drivers are new for this report, adapted from the shipped `run_kuzu.py`; they live only in the sandbox, not in your archive.
